# CP07.1 System Hardening

## A. What was audited

Read the project directives, roadmap, scope/readiness/checksheet, research matrix and synthesis, then inspected the workflow engine/validator, event schema, metrics, temporal decoder, training objectives, experiment configurations, tests, model paths, workflow draft and repository hygiene. The detailed pre-change baseline is in `CP07.1_context_and_audit.md`.

## B. Confirmed issues

- The workflow engine accepted only enumerated `valid_paths`; it had no prerequisite/partial-order representation.
- Non-sufficient observations were reflected in status/violation output but not retained in an event-history collection.
- The future-action skip handler sliced skipped steps using the first candidate position instead of the selected candidate route's own position. The regression fixture with two candidate routes at different positions reproduced the wrong reported steps.
- Benchmark metrics silently truncated mismatched label sequences.
- Benchmark callers and CP06 diagnostics treated class ID 0 as background even though background is a configured action label.
- Framewise training uses class-weighted cross entropy; MS-TCN uses the stage-wise `mstcn_loss`. Their historical comparison is not a pure architecture-only comparison.
- `.gitignore` lacked `.idea/`; repository index inspection found no tracked `.idea/` entries. Some help/package/workflow documentation retained CP01-era wording.

## C. Changes implemented

- Added prerequisite-DAG mode to the existing workflow engine and validator. Route mode remains supported; the validator disallows mixing the two forms.
- Added deterministic synthetic tests for both valid orders, prerequisite rejection, DAG cycle/acceptance validation, and route skip selection.
- Skip handling now reports only the steps between the selected candidate position and matched action, and resumes after the action that was observed.
- The engine retains every received `ActionEvent` in `observations`, including uncertain and malformed events. The existing `events` list remains the evidence-valid input history presented for workflow interpretation; actual route/DAG progress is represented separately by workflow state. Confidence, evidence status, and workflow acceptance remain separate.
- Metrics now reject unequal sequence lengths and non-1D inputs, reject out-of-vocabulary IDs, and require background semantics explicitly by configured label or class ID. Pipeline and training evaluation pass the configured background label; CP06 analysis resolves the configured `NULL` class index.
- Added tests for equal/mismatched/empty lengths, a nonzero background ID, and uncertain observation retention without state advancement.
- Added `.idea/` to `.gitignore` without deleting machine-local files. Updated stale package/help/workflow README wording. No workflow draft or human worksheet edits were made.

## D. Changes intentionally not implemented

- No `Disassembly_A` route or prerequisite graph, executable YAML, duration rule, timeout, conditional path, or completion semantics was created.
- No temporal decoder redesign or held-out-test tuning was performed. Existing smoothing/short-run merging behavior is deterministic and existing temporal tests pass; its known limitation is heuristic boundary modification, and untested malformed-array/timebase edge cases remain technical debt rather than a confirmed defect in this checkpoint.
- No model retraining, new baseline, metric regeneration, or checkpoint replacement was performed.
- No process compliance/anomaly metric is claimed.

## E. Workflow architecture decision

Partial-order capability is needed because some procedure specifications express prerequisites rather than one canonical total order. The smallest extension is one engine with two explicit config forms: `valid_paths` or `required_actions` + `prerequisites`. The schema and behavior are documented in `CP07.1_workflow_design.md`. Prerequisites permit independent actions in either order without enumerating each route. Human-approved workflow semantics, optional/conditional/rework behavior, and any actual `Disassembly_A` graph remain human-dependent.
