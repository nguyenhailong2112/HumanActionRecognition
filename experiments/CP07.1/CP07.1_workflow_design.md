# CP07.1 Workflow Architecture Decision

## Decision

Keep one `WorkflowEngine` and add a second normalized input representation: `prerequisites` plus `required_actions`. Keep `valid_paths` for workflows whose approved semantics are naturally route-based. A configuration must choose one representation; the validator rejects mixed route and prerequisite forms.

## Prerequisite schema

```yaml
workflow:
  id: synthetic-example
  required_actions: [A, B, C]
  prerequisites:
    A: []
    B: []
    C: [A, B]
```

This is a schema example only. It is not a proposed `Disassembly_A` graph.

The engine stores the actions accepted for the current worker/execution. An action is eligible when all its configured prerequisites have been accepted. Thus either A/B order is allowed and C becomes eligible after both. An action attempted before its prerequisites is retained as an observation, produces an invalid-transition and skipped-prerequisite record, and does not advance the accepted-action state. Completion means all configured `required_actions` have been accepted.

The validator checks required-action coverage, vocabulary references, duplicate/self prerequisites, and cycles. A cycle is rejected because it cannot reach completion. The configuration still must pass the existing approval, disposition, completion, and timing-policy validation before real execution.

## Scope and limitations

- Partial-order semantics represent mandatory actions and prerequisites only.
- Optional actions, branches, rework, and repeat semantics remain represented by the existing explicit route form; the DAG form does not infer or provide these rules.
- The engine is a deterministic interpreter, not a model and not process-performance ground truth.
- Confidence remains descriptive. It is not calibrated and does not establish evidence sufficiency.
- No action or prerequisite values are supplied for `Disassembly_A`; the draft and human worksheet remain untouched.
